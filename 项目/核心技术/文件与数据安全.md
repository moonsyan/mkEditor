# Markdown 编辑器文件与数据安全

> 标签：#markdown编辑器 #文件系统 #数据安全 #本地优先
> 日期：2026-08-06

## 数据分类

| 数据 | 位置 | 丢失影响 | 策略 |
| --- | --- | --- | --- |
| Markdown 正文 | 用户选择路径 | 极高 | 原子保存、冲突检测、恢复副本 |
| 附件 | 用户工作区 | 高 | 先写成功再插入引用 |
| 恢复草稿 | Electron userData | 高 | 定期写入、成功保存后延迟清理 |
| 设置 | userData | 低 | schema 版本与默认值 |
| 最近文件 | userData | 低 | 路径失效可恢复 |
| 日志 | userData/logs | 低 | 不写正文和敏感路径 |

## 文件快照

```ts
type FileRef = {
  id: string;
  displayPath: string;
};

type FileVersion = {
  mtimeMs: number;
  size: number;
  contentHash: string;
};

type FileSnapshot = {
  file: FileRef;
  content: string;
  version: FileVersion;
  textFormat: {
    encoding: 'utf-8';
    bom: boolean;
    eol: 'lf' | 'crlf';
    finalNewline: boolean;
  };
};
```

MVP 正式支持 UTF-8，可识别 UTF-8 BOM。检测到其他编码时默认只读或要求用户以 UTF-8 另存，不能用错误编码直接覆盖。

`contentHash` 对磁盘原始字节计算，而不是对已规范化的 JavaScript 字符串计算，因此 BOM、EOL 和末尾换行变化都能进入版本判断。算法固定并写入实现文档；它用于冲突检测，不作为对抗恶意输入的安全签名。

## 文件能力

Main 在用户通过原生对话框打开文件后生成随机 `fileId`，按受信主 frame 所属窗口保存 `fileId -> canonicalPath` 映射。Renderer 的 `displayPath` 只用于标题和提示，不是授权凭据。

- 保存和监听只接受 `fileId`；
- 另存为由 Main 打开原生对话框，成功后签发新的 `fileId`；
- 工作区操作使用 `workspaceId + relativePath`，Main 解析真实路径并验证没有越界；
- 窗口关闭、导航到非应用文档或授权撤销时回收能力；
- Main 可以在最近文件和恢复记录中保存真实路径，但重新打开时必须因明确用户动作重新签发能力。

## 保存协议

1. `DocumentSession` 捕获 `savedRevision` 和当前内容，每个会话最多允许一个保存请求在途；
2. Renderer 提交 `fileId + expectedVersion + content + requestId`；
3. Main 校验主 frame、schema、内容大小和 `fileId` 能力，并按 `sender + requestId` 幂等去重；requestId 首次出现时绑定 payload 摘要，复用同 ID 却提交不同内容必须拒绝；
4. Main 读取目标原始字节版本，与 `expectedVersion` 不一致则返回 `CONFLICT`；
5. 在同目录创建不可预测名称的临时文件，按原 BOM、EOL 和末尾换行规则编码；
6. 写入并关闭临时文件句柄，尽能力执行 flush；
7. 替换前再次读取目标版本；若发生变化，保留原文件、删除或隔离临时文件并返回 `CONFLICT`；
8. Windows 上执行经过验证的替换流程，并保留可恢复的前一版本；
9. 回读目标原始字节，确认哈希等于准备写入的字节；无法确认时返回 `SAVE_OUTCOME_UNKNOWN`，保留诊断 ID 和恢复材料，不能标记保存成功；
10. Main 返回回读得到的新 `FileVersion`；Application 即使保存的是旧 revision 也先更新 `diskVersion`；
11. 只有 `currentRevision === savedRevision` 时才清除 dirty，并且只清理 `draftRevision <= savedRevision` 的恢复草稿；否则保持 dirty、保留较新草稿并合并安排下一次保存。

临时文件必须和目标在同一卷，避免跨卷移动失去原子性。Windows 杀毒软件、索引器或其他进程可能短暂占用文件，可对明确的共享冲突做少量带抖动重试，但不能无限重试。

版本比较与文件替换在通用 Node `fs` 中不是原子 compare-and-swap，步骤 7 只能缩小竞态窗口，不能凭它宣称数学意义上的零竞态。阶段 1 必须验证 Windows 替换实现能否在替换时保留前一目标版本；稳定版发布说明应承诺“检测已知外部变化并保留可恢复版本”，不能宣称与所有外部编辑器并发时绝对不会发生竞态。

### 不同编辑模式的保存内容

- 实时模式：通过 editor 模块的 Milkdown serializer 取得 Markdown 字符串；
- 安全源码兜底和完整源码模式：直接读取当前源码控件中的 Markdown 字符串，不经过 serializer；
- 两种模式随后都进入同一个 `DocumentSession -> FilePort -> main/file` 保存协议，执行 expectedVersion 比较、文本格式恢复、原子替换和恢复草稿清理；
- 模式切换只有在 parse/serialize 成功后才转移正文权威，失败时保留原模式和原内容。

安全源码兜底不是绕过冲突检测的第二条写盘通道。无论正文来自哪种编辑模式，`main/file` 都是唯一写入用户正文的模块。

## 冲突判定

mtime 和 size 只是快速判断，原始字节内容哈希用于最终确认。若 mtime 改变但字节哈希和文本格式完全一致，可以刷新基线而不制造冲突；内容或文本格式发生变化才视为外部修改。以下情况视为冲突：

- 文件内容发生外部变化；
- 文件被移动、删除或替换；
- 磁盘版本未知且当前会话 dirty；
- 文件监听报告变化但无法证明是自身写入。

冲突选项：

- 查看当前版本与磁盘版本；
- 重新加载磁盘版本；
- 另存当前版本；
- 明确确认后覆盖；
- 后续增加文本差异和三方合并。

MVP 不需要自动三方合并，但必须保证两个版本都可恢复。

“确认覆盖”不能实现为绕过检查的 `force=true`。用户确认时记录刚展示的磁盘 `FileVersion`，覆盖请求把它作为新的 `expectedVersion` 重新执行完整保存协议；如果确认后文件再次变化，必须再次进入冲突。

## 自身写入抑制

保存后文件监听必然收到变化。不能简单按 1 秒时间窗口忽略所有事件，否则可能吞掉真实外部修改。

建议记录：

```ts
type OwnWrite = {
  requestId: string;
  fileId: string;
  canonicalPath: string;
  expectedHash: string;
  completedAt: number;
};
```

收到事件后重新读取元数据或哈希，只有与自身写入结果匹配才抑制。rename、unlink、权限变化仍需上报。

## 恢复草稿

恢复数据不直接覆盖原文件。已有文件的草稿键由 Main 持有的规范化路径哈希和会话 ID 组成；未另存的新文档只使用会话 ID。另存为成功后再迁移草稿身份，失败时继续保留原草稿。内容包括：

- 原路径和脱敏显示名；
- 基线文件版本；
- 当前权威模式；
- 实时模式保存 ProseMirror Document JSON，源码模式保存原始 Markdown 字符串；
- 实时模式可附带最近一次成功生成的 Markdown fallback，但恢复不能只依赖 serializer 成功；
- 文档 revision；
- 最后更新时间；
- 应用和 schema 版本。

恢复草稿本身使用临时文件加替换的方式原子写入，并带 schema 版本、内容校验值和 `draftRevision`。内容变化后按最大间隔节流写入，例如每 3～5 秒一次，不能只在停止输入后 debounce；composition 期间不抓取快照，不为每次 transaction 序列化整篇文档。Main 确认写入成功后返回 checkpoint revision 和时间，界面才能显示“已恢复保护”。应用退出前尽力 flush。启动时检测未正常关闭的草稿，提供恢复、另存和丢弃。

恢复时先验证草稿 schema 和校验值。实时 JSON 能被当前 schema 读取时直接恢复；否则尝试 Markdown fallback 并进入安全源码兜底。两者都失败时保留原草稿并导出诊断，不删除、不覆盖用户文件。

恢复目标是“最多回到最近一次成功写入的草稿检查点”，不是强杀前最后一个按键零丢失。默认恢复点目标 RPO 为 5 秒：界面应能显示最后草稿时间；强杀或断电可能丢失该检查点之后的输入。若 1 MB 文档无法在不干扰输入的前提下达到该目标，应基于测量调整节流、移入 Worker 或明确放宽大型文档 RPO。

草稿保留策略必须可配置。默认只清理已经成功保存、`draftRevision <= savedRevision` 且超过宽限期的记录；旧 revision 保存完成不得删除包含较新输入的草稿。

## 自动保存

自动保存不是 MVP 第一优先级。启用前必须满足：

- roundtrip 已稳定；
- 冲突检测已实现；
- 恢复草稿已实现；
- 保存期间继续输入不会错误清 dirty；
- 不支持语法文件默认不自动保存。

建议默认“停输 2 秒后保存”，并设置最短保存间隔，切换标签和窗口失焦只触发一次请求。不能为每次 transaction 写磁盘。

## 附件写入

图片粘贴流程：

1. 读取剪贴板图片并限制格式、尺寸和字节数；
2. 计算内容哈希，生成安全文件名；
3. 解析并校验目标附件目录在授权范围内；
4. 原子写入附件；
5. 成功后计算相对 Markdown 路径；
6. 最后提交图片节点 transaction。

如果第 4 步失败，正文中不能出现一个看似成功但实际不存在的图片引用。删除正文图片时默认不自动删除附件，资源清理必须是独立、可预览操作。

## 路径策略

- 所有内部比较使用规范化绝对路径；
- Markdown 中优先保存 `/` 分隔的相对路径；
- 拒绝 NUL、保留设备名和非法 Windows 文件名；
- 防止 `..` 越过授权根目录；
- 明确处理符号链接和 junction，不能只做字符串前缀比较；
- 重命名文档时不在 MVP 自动批量改写所有引用。

## 删除策略

第一版文件删除进入系统回收站，不能直接永久删除。删除前显示目标和未保存状态；失败后不能从文件树投影中消失。

## 故障注入测试

必须模拟：

- 写到一半磁盘满；
- 目标文件只读；
- 临时文件被占用；
- 保存前外部修改；
- 保存完成回包前 renderer 崩溃；
- 保存期间连续编辑并触发下一次合并保存；
- 相同 requestId 重复到达，以及同 ID 携带不同 payload；
- 初次版本检查后、最终替换前发生外部修改；
- 用户确认覆盖后文件再次发生变化；
- 写入成功但回读确认失败；
- 旧 revision 保存成功时存在更高 revision 的恢复草稿；
- serializer 失败时仍能用 ProseMirror JSON 恢复；
- schema 升级后 JSON 无法读取时回退 Markdown 或保留原草稿；
- rename/replace 失败；
- 文件被删除或目录被移动；
- 附件写成功但编辑 transaction 失败。
