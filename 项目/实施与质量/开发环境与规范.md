# Markdown 编辑器开发环境与规范

> 标签：#markdown编辑器 #typescript #工程规范 #electron
> 日期：2026-08-06

## 工具链原则

使用项目创建时与 electron-vite 兼容的 Node Active LTS 作为开发和 CI 工具链，版本写入 `.nvmrc` 或 `.node-version`；Electron 主进程运行时使用 Electron 自带的 Node 版本，两者必须分别记录，不能假设完全相同。通过 `packageManager` 字段固定 pnpm 版本；当前 Node 若提供 Corepack 则显式启用，否则在 CI 安装该精确版本。不要依赖开发机碰巧存在的全局构建工具。

该项目不需要 JDK。只有未来加入 Java 服务端模块时，才按 Java 项目规则单独配置 JDK 17。

## 建项步骤

1. 创建 Electron + React + TypeScript 脚手架；
2. 立即开启 TypeScript strict；
3. 配置 ESLint、Prettier、Vitest；
4. 建立 main/preload/renderer 三个 tsconfig 或明确构建边界；
5. 设置路径别名但避免跨层随意导入；
6. 建立最小 Playwright Electron 启动测试；
7. 配置 CI 执行 lint、typecheck、test、build；
8. 创建 `docs/adr`，只记录初始技术路线、持久化和安全边界等需要长期追溯的决策。

## 推荐脚本

```json
{
  "scripts": {
    "dev": "electron-vite dev",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format:check": "prettier --check .",
    "test": "vitest run",
    "test:e2e": "playwright test",
    "build": "electron-vite build"
  }
}
```

具体命令以脚手架版本为准，建项时通过官方文档确认。

## TypeScript 规则

- `strict: true`；
- 业务与边界代码不使用 `any` 绕过类型检查；确有缺失类型的第三方适配应隔离在单一 adapter 中，用 `unknown` 收窄并写明原因；
- IPC、配置文件、恢复草稿等不可信或跨版本输入必须有运行时 schema，类型声明不能替代运行时验证；纯内部函数参数不机械重复运行时校验；
- 使用判别联合表达错误和状态；
- 避免非空断言 `!`；
- domain/core 不导入 Electron 和 React；
- shared 只放真正跨 main/renderer 的 DTO，不做杂物目录。

## 状态规则

- 服务器状态概念不适用于本地正文，不引入 React Query；
- Zustand 只保存应用壳投影；
- ProseMirror EditorState 留在编辑器；
- React component state 保存局部 UI 状态；
- 文件保存状态由 DocumentSession 状态机管理；
- dirty、saving、conflicted、recovery 在 Zustand 中只能是 `DocumentSession` 快照的只读投影，UI 通过 Application 命令触发迁移；
- 不复制同一状态到多个 store。

## 代码风格

遵循全局约定：除 `} catch` 外，右花括号后换行；循环中在不改变逻辑的前提下优先提前 `continue`，减少 `else`。

此外：

- 函数短小并用领域词命名；
- 注释解释原因和约束，不复述代码；
- 不提前创建 `Manager`, `Utils`, `Common` 大类；
- 一次 PR 只解决一个可验收问题；
- 新依赖必须说明用途、维护状态、包体和替代方案；
- 编辑器 schema 变更必须带 fixture 和迁移说明。

## Git 规范

提交信息遵循用户全局规范：

```text
<type>: <摘要> #<PM号>
```

允许的 type：`feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore`。没有 PM 号时不要伪造，先建立项目内部 issue 编号规则或由用户提供 PM 号。

分支建议：

```text
main
feature/<issue>-short-name
fix/<issue>-short-name
```

不长期维护 develop 分支。小团队用短分支和受保护 main 更简单。

## 分级验证与 CI

单人开发不要求每次本地提交执行整套 Electron 和人工回归：

- 日常提交：受影响的 typecheck、lint、单元测试和 Markdown fixture；
- 合并到主分支或阶段里程碑：完整 typecheck、lint、unit/fixture、核心 Electron 主链路和 build；
- 候选发布：完整 E2E、性能基准、安全清单、Windows 人工 IME 与安装升级检查。

核心 Electron 主链路至少覆盖“打开 -> 编辑 -> 保存 -> 强杀 -> 恢复”，外加外部修改不得被覆盖。Playwright Electron 若因当前版本限制无法稳定自动化，必须保留可重复脚本或人工检查单和结果记录，不能用空缺的自动化门禁阻塞所有开发，也不能把“未覆盖”写成“已通过”。

CI 推荐顺序：

```text
install --frozen-lockfile
  -> typecheck
  -> lint + format check
  -> unit + fixture
  -> renderer/electron E2E
  -> build
  -> artifact smoke test
```

发布构建应在干净 CI 环境完成，不从开发机手工打正式包。

## 版本和依赖升级

- 普通依赖小步升级；
- Electron、React、Milkdown、ProseMirror 大版本单独 PR；
- 编辑器、React 或 Electron 大版本升级在合并前跑最小 IME 冒烟，在候选发布前跑完整人工 IME 回归；普通补丁升级根据变更说明和影响范围决定；
- 升级前记录基线性能；
- lockfile 异常大范围变化必须解释；
- 不使用 `latest` 作为可重复构建依赖范围。

## Definition of Done

日常功能完成：

- 类型检查和受影响测试通过；
- 需求验收条件通过；
- 新行为有与风险相称的测试，或说明只能人工验证的原因；
- 文档、功能设计或 issue 已同步。

候选发布在此基础上增加：

- 类型检查、lint、测试和构建通过；
- 没有新增高危安全配置；
- 性能敏感变化有测量；
- 用户数据格式变化有兼容与恢复方案。

ADR 只在达到 [[架构决策模板]] 所述触发条件时同步，不作为每个功能的固定文档作业。
