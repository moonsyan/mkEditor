# Markdown 编辑器技术选型与决策

> 标签：#markdown编辑器 #技术选型 #electron #prosemirror
> 日期：2026-08-06

## 决策原则

选型首先降低编辑器和数据安全风险，其次降低 Java 开发者的学习成本，最后才考虑安装包大小和理论性能。所有依赖锁定精确版本并提交 lockfile，不在架构文档中写死很快过时的版本号。

## ADR-001 使用 Electron

**状态：接受，至少持续到第一个稳定版。**

选择原因：

- ProseMirror、Milkdown、CodeMirror 等生态直接运行；
- 文件对话框、菜单、打印 PDF、剪贴板和自动更新方案成熟；
- TypeScript 可以覆盖 UI 到 preload 的主要边界；
- 对单人开发更容易定位问题。

代价是安装包和内存较大。第一版不规划迁移 Tauri，因为迁移会重写窗口、IPC、文件、打印、插件和更新部分，并不是替换一层壳。

## ADR-002 React + TypeScript

**状态：接受。**

React 只负责应用壳和声明式 UI，不控制 ProseMirror 高频输入。TypeScript 开启 `strict`，IPC DTO、领域错误、命令和设置必须有明确类型，禁止用 `any` 绕过边界。

## ADR-003 Milkdown 作为首选编辑器框架

**状态：试行，必须通过阶段 0 技术验证。**

Milkdown 已把 Markdown 处理、ProseMirror 和插件机制组合起来，适合 Markdown 优先的产品。应用层只通过 editor/codec 适配接口调用 Milkdown 提供的 parse/serialize 能力，不再自建一套 remark 与 ProseMirror 的转换桥。remark/mdast 可以作为 Milkdown 内部实现和扩展机制存在，但不是应用层的第二套文档模型。Milkdown 能减少基础 schema、parser、serializer 的搭建工作，但不会消除 ProseMirror 学习成本。

验收条件：

- L0 语法往返满足 [[Markdown兼容策略]]；
- 中文 IME、撤销、粘贴和嵌套列表稳定；
- 能实现至少一个复杂块 NodeView 原型；
- 能实现“当前块显示部分 Markdown 标记”的可行性原型；
- 1 MB 文档有可接受的降级路径。

失败后的顺序：

1. 先降低局部标记显隐要求，保留 Milkdown；
2. 若 Markdown 映射本身受限，评估直接使用 ProseMirror；
3. 只有明确证据表明 Tiptap 更合适时才替换，不能因为 API 看起来简单就迁移。

## ADR-004 ProseMirror Document 是实时模式唯一运行时模型

**状态：接受。**

不创建另一套完整 `EditorDocument`。Milkdown 在 parse/serialize 期间产生的 remark AST 只作为临时转换对象，应用代码不长期持有，也不直接同步它。应用状态只保存会话元数据。这样减少三份模型之间的映射、缓存失效和撤销一致性问题。

## ADR-005 Markdown 是持久化格式

**状态：接受。**

正文不进入私有数据库。应用数据库只允许保存最近文件、窗口位置、设置、搜索索引和恢复信息；这些数据删除后不能导致正文丢失。

第一版承诺语义级往返，不承诺逐字符无损。详见 [[Markdown兼容策略]]。

## ADR-006 Zustand 只管理壳层状态

**状态：接受。**

可以进入 Zustand：

- 当前会话 ID、标签页元数据；
- 主题、设置、对话框状态；
- 文件树投影、大纲投影；
- dirty、保存中、冲突和恢复状态的只读 UI 投影。

这些投影的写入权威仍是 Application 层的 `DocumentSession`。Zustand 只订阅会话快照，UI 操作必须调用 Application 命令，由 `DocumentSession` 完成状态迁移；禁止组件或 Zustand action 直接修改 dirty、saving、conflicted、recovery。投影可以重建，不能反向决定保存和冲突逻辑。

不能进入 Zustand：

- 每次按键；
- 完整 ProseMirror EditorState；
- selection 的每次变化；
- 整篇 Markdown 正文；
- NodeView 内部临时状态。

## ADR-007 不在 MVP 开放插件系统

**状态：接受。**

内部可以按扩展注册命令、schema、NodeView 和导出器，但不承诺稳定公共 API，也不加载第三方代码。插件一旦开放，就必须同时解决版本、隔离、权限、签名、崩溃和升级兼容，成本远高于定义一个 `Plugin` 接口。

## ADR-008 生产 CSP 中的内联样式只作为临时例外

**状态：有条件接受，稳定版前复审。**

生产环境默认目标是不使用 `'unsafe-inline'`。若 Milkdown、CodeMirror 或主题机制在当前版本确实需要内联样式，可以临时仅对 `style-src` 放开，并记录触发该例外的依赖、验证过的替代方案和移除条件；`script-src` 不得因此放开。优先顺序是抽取静态样式、使用带 nonce 的受控 `<style>`，再评估精确 hash。稳定版发布前必须重新验证能否移除该例外。

## 工具选择表

| 能力 | 选择 | 备注 |
| --- | --- | --- |
| 包管理 | pnpm + Corepack | 锁定 packageManager 字段 |
| 构建 | electron-vite | 分离 main、preload、renderer |
| UI | React | 不包裹编辑器高频事务 |
| 状态 | Zustand | 小而明确的 slice |
| 编辑器 | Milkdown | 阶段 0 后正式确认 |
| 文档模型 | ProseMirror | 运行时唯一模型 |
| Markdown | Milkdown parser/serializer | 内部使用 remark/unified；应用层不另建转换桥 |
| 安全源码兜底 | 原生文本控件或最小实现 | 阶段 1，仅处理解析失败和高风险语法 |
| 完整源码编辑 | CodeMirror 6 | 阶段 3 引入 |
| 代码高亮 | 初期轻量方案 | Shiki 放 Worker 或延迟渲染后再评估 |
| 数学 | KaTeX | 第三阶段 |
| 图表 | Mermaid | 第三阶段，必须隔离和限制 |
| 测试 | Vitest + Playwright | 关键编辑行为用真实浏览器 |
| 格式化 | ESLint + Prettier | 自动化，不争论个人风格 |
| 发布 | electron-builder 或 Electron Forge 二选一 | 技术验证后用安装需求决定 |

## 不选择的方案

### JavaFX

JavaFX 可以写桌面壳，但缺少与 Web 编辑器生态同等级的 Markdown 富编辑内核。最终仍需要嵌入 WebView，增加 Java 与 JavaScript 两套状态和通信，收益有限。

### Monaco

更适合完整代码编辑器。Markdown 源码模式使用 CodeMirror 6 更轻，并且扩展与嵌入成本更低。

### Slate 和 Quill

Slate 自由度高但需要更多自研；Quill 面向常规富文本，Markdown 文档结构与往返转换不是它的核心优势。

### 从第一天使用 Monorepo

第一版只有一个应用，没有真实独立发布单元。先使用单仓库清晰目录；当编辑器需要被 Web 或其他应用复用时再引入 workspace。

## 决策复审时机

- 阶段 0 结束：复审 Milkdown；
- 第一次发布前：复审打包和自动更新方案；
- 稳定版发布前：复审 CSP 内联样式例外；
- 出现 Web 端需求时：复审 package 拆分；
- 出现第三方扩展需求时：单独设计插件安全模型；
- 性能数据连续超预算时：基于 profile 复审技术，而不是凭感觉迁移。
