# 本地优先 Markdown 编辑器项目蓝图

> 标签：#markdown编辑器 #electron #架构 #本地优先
> 日期：2026-08-06

## 一句话结论

第一版建设一个 **Windows 优先、本地文件优先、语义可靠优先** 的 Markdown 桌面编辑器。技术栈固定为 Electron + React + TypeScript，编辑器先用 Milkdown 快速验证；运行时编辑模型由 ProseMirror 提供，Markdown 转换由 Milkdown 的 parser/serializer 适配层提供。remark 是该转换链路的内部机制，应用层不重复搭建 remark 与 ProseMirror 的桥。

不要把第一版定义成完整 Typora 克隆。第一阶段只证明三件事：

1. 中文输入、光标、选区、复制粘贴和撤销重做可靠。
2. Markdown 打开、编辑、保存后不丢内容，已声明支持的语法语义不变。
3. 文件写入、冲突检测和崩溃恢复不会伤害用户数据。

## 项目定位

目标用户首先是自己和普通技术写作者，核心任务是：

- 打开本地 `.md` 文件并稳定编辑；
- 使用接近所见即所得的方式写标题、段落、列表、引用、链接、图片和代码；
- 保存为可被 Typora、Obsidian、VS Code 和 Git 继续使用的 Markdown；
- 即使应用崩溃、文件被外部修改，也能恢复或明确处理冲突。

不把账号、云同步、多人协作、知识图谱、AI、插件市场作为第一版目标。详细边界见 [[产品范围与原则]]。

## 核心技术决策

| 领域 | 第一版决定 | 原因 |
| --- | --- | --- |
| 桌面外壳 | Electron | Web 编辑器生态成熟，文件、打印和打包路径明确 |
| UI | React + TypeScript | 生态成熟，类型系统能约束 IPC 和状态边界 |
| 编辑器 | Milkdown | Markdown 优先，已组合 ProseMirror 与 remark，适合快速验证 |
| 编辑器底座 | ProseMirror | 文档树、事务、选区、历史和扩展能力成熟 |
| Markdown | Milkdown parser/serializer | 内部集成 remark/unified，应用层只依赖统一 codec 接口 |
| 应用状态 | Zustand | 只管理壳层状态，不接管编辑器高频状态 |
| 构建 | electron-vite + pnpm | 主进程、preload、renderer 边界清晰 |
| 测试 | Vitest + Playwright | 同时覆盖纯逻辑与真实 Electron 交互 |

这些不是永久不可变的决定。只有改变技术路线、跨模块契约、持久化格式或安全边界时，才通过 [[架构决策模板]] 记录证据和迁移成本；普通实现选择写进功能设计、issue 或代码即可。详细取舍见 [[技术选型与决策]]。

## 核心架构

```text
用户
  |
React App Shell
  |-- 文件、标签页、大纲、设置
  |
Editor Module
  |-- Milkdown / ProseMirror
  |-- Milkdown Markdown Adapter
      |-- parse / serialize（内部使用 remark）
  |
Document Service
  |-- 会话、dirty、保存、冲突、恢复
  |
Typed Preload API
  |-- 只允许白名单命令
  |
Electron Main
  |-- 文件系统、窗口、菜单、打印、系统集成
```

依赖只能向下，React 组件不能直接调用 Node `fs`，编辑器事务不能进入 Zustand，主进程不能理解 React 或 ProseMirror 视图。完整说明见 [[总体架构]]。

- 编辑器 parse/serialize、模式切换契约：[[编辑器内核设计]]；

## 唯一真相规则

不同阶段有不同的权威数据，但同一时刻只能有一个编辑权威：

- 磁盘持久化格式：Markdown 文本；
- 实时编辑模式：ProseMirror Document 是当前会话权威；
- 源码模式：Markdown 字符串是当前会话权威；
- 模式切换：必须执行 serialize 或 parse，并在成功后转移权威；
- 保存完成：记录内容哈希、mtime、文件大小和保存版本。

不要同时维护 Markdown AST、业务 `EditorDocument` 和 ProseMirror Document 三份长期状态。详见 [[编辑器内核设计]]。

阶段 1 的源码能力仅是解析失败或高风险语法文件的安全兜底，可以使用最小文本控件，不包含语法高亮、完整快捷键或分屏。阶段 3 才正式引入 CodeMirror 6，建设完整源码模式。阶段归属以 [[开发路线图]] 为准。

## 功能分层

### 阶段 1：单文档安全 MVP

- 打开、编辑、保存单个 `.md` 文件；
- 段落、H1-H6、粗体、斜体、行内代码；
- 无序列表、有序列表、引用、分隔线、代码块；
- 链接和本地图片；
- 撤销重做、复制粘贴、查找；
- dirty 提示、手动保存、恢复草稿；
- 外部修改检测和冲突处理；
- 解析失败或高风险语法文件的安全源码兜底；
- Windows 安装包；
- 基础浅色和深色外观。

### 阶段 2：桌面写作 MVP

- 删除线、任务列表和自动链接；
- 文件夹和文件树；
- 多标签页；
- 自动保存；
- 图片粘贴到附件目录；
- 大纲；
- HTML/PDF 导出；

### 阶段 3：高级写作体验候选

- 表格可视化编辑、脚注、Frontmatter、数学公式、Mermaid；
- 局部 Markdown 标记显隐；
- 完整源码模式和分屏模式；
- 大文档降级与延迟高亮。

### 稳定版后独立立项

- 插件 SDK、主题市场；
- SQLite 全文索引、Git、同步、AI。

## 技术验证门槛

正式建设 UI 前，必须完成一个可以被丢弃的验证程序：

1. 使用 50 份 Markdown fixture 完成 `Markdown -> Editor -> Markdown` 测试，转换只通过 Milkdown 适配层执行。
2. 连续输入中文 30 分钟，无重复上屏、光标跳动或撤销异常。
3. 验证段落、嵌套列表、代码块、链接、图片的复制粘贴。
4. 验证 100 KB、500 KB 和 1 MB 文档的打开与输入响应。
5. 验证 Milkdown 能否实现产品需要的局部标记显示原型。

若第 5 项失败，先降低产品体验目标；只有在核心商业价值确实依赖该体验时，才进入直接扩展 ProseMirror 的路线。

## 项目完成定义

MVP 不是“功能都能点”，而是同时满足：

- 支持语法的兼容性 fixture 全部通过；
- 核心编辑 E2E 在 Windows 连续通过；
- 应用强制结束后可以恢复到最近一次成功草稿检查点，普通文档默认 RPO 不超过 5 秒；
- 已检测到的外部修改不会被静默覆盖，保存关键窗口保留可恢复的前一版本；
- 主进程安全配置和 IPC 白名单检查通过；
- 1 MB 文档超出性能预算时有明确降级，而不是卡死；
- 安装、升级、卸载不会删除用户 Markdown 和附件。
